# RailSaathi

AI-assisted safety and assistance for Mumbai local train commuters. This repo
currently implements the **`/chat` assistant**: a multilingual (English /
हिन्दी / मराठी), streaming chat with typed and voice input, grounded in a small
verified knowledge base.

> ⚠️ All safety content and helpline numbers in `src/data/intents.json` and
> `src/lib/helplines.ts` are **draft placeholders** and must be verified against
> official RPF / GRP / Indian Railways sources before any real use.

## Running

```bash
npm install
npm run dev        # http://localhost:3000/chat
```

The chat works out of the box with **no API key** using a small demo stream. To
use the real LLM, put these in `.env.local` at the **project root** (Next.js
does not read `src/.env`):

```bash
# .env.local  (server-only; never commit real keys)
GROQ_API_KEY=your_groq_key
GROQ_MODEL=openai/gpt-oss-120b          # tool-capable; see note below
GROQ_FALLBACK_MODEL=openai/gpt-oss-20b  # retried once if the primary fails

# Timetable sync only (never called at request time by the app)
RAILRADAR_API_KEY=your_railradar_key
RAILRADAR_MONTHLY_BUDGET=300
```

Model note: the models a Groq account can use vary. Check `GET /openai/v1/models`
with your key and set `GROQ_MODEL`/`GROQ_FALLBACK_MODEL` to a **tool-capable**
model you have access to (e.g. `openai/gpt-oss-120b`, or `llama-3.3-70b-versatile`
if enabled). Tool calling (train schedules) needs a tool-capable model.

- With `GROQ_API_KEY` set, **every** reply is generated by the LLM. Retrieval
  from `intents.json` only adds context to the prompt; it is never shown
  verbatim and never used to refuse.
- Without a key, a short demo-mode note streams so the UI still works.

Useful scripts: `npm run build`, `npm run lint`, `npm run sync-timetable`.

## Features

- **LLM answers everything** in scope (safety, ticketing, schedules, refunds,
  disruptions, general Indian Railways basics). Politely declines off-topic.
- **Multilingual + Hinglish**: reply language follows the selector (English /
  हिन्दी / मराठी); if the selector is English but the user writes Hinglish
  (Roman-script Hindi), the model mirrors Hinglish.
- **Switch language mid-chat**: changing the selector inserts a "Language
  changed to …" divider, re-translates the latest follow-up chips, updates the
  mic locale (restarting it if listening), and applies to the next message
  without aborting an in-flight stream. Language is stored per chat.
- **Translate** action on each assistant bubble → `POST /api/translate`
  (temperature 0; preserves numbers, phone numbers, times and list formatting).
  Cached per language; toggles back to the original.
- **Train schedules via tool calling**: the model calls server-side tools that
  read a local timetable store. Times come only from tool data — never guessed.
  Results render as a `<TrainResultCard />` with a live "Next in N min".

## The `/api/chat` event protocol

`POST /api/chat`

```jsonc
// request body
{
  "lang": "en" | "hi" | "mr",
  "messages": [{ "role": "user" | "assistant", "content": "string (<=500 chars)" }]
}
```

Response: `text/plain; charset=utf-8`, streamed. The body is the answer text,
followed by a single marker line and a JSON array of follow-up questions:

```
<answer tokens streamed here...>

[[FOLLOWUPS]]["Question 1","Question 2","Question 3"]
```

- `[[TRAINS]]{json}` — optional, only for schedule answers; emitted **before**
  the follow-ups block. Carries the structured `get_next_trains` result plus
  source/effective-date metadata for the `<TrainResultCard />`.
- `[[FOLLOWUPS]]` — normal suggested follow-ups (rendered as small pill chips).
- `[[CHOICES]]` — used when the answer is a clarifying question; the client
  renders these as larger primary-outline choice buttons.

Full trailer order:

```
<answer text>
\n\n[[TRAINS]]{ "from","to","effectiveFrom","sourceName","syncedAt","result" }
\n\n[[FOLLOWUPS]]["q1","q2","q3"]
```

`POST /api/translate` → `{ text }`. `GET /api/train?trip_id=…` → full stop list.

The client (`parseAssistantStream` in `src/lib/chat-protocol.ts`) strips the
marker from the visible text as it streams — including any partial marker at the
end of a chunk — and turns the array into chips once the stream completes.

Response headers:

| Header             | Meaning                                                        |
| ------------------ | -------------------------------------------------------------- |
| `x-urgency: high`  | Urgency keywords detected. The client shows `<EmergencyBanner />` immediately, independent of the model text. |

Status codes: `200` stream, `400` invalid body, `429` rate limited
(`retry-after` header, 20 requests/minute/IP, in-memory).

### Server request flow (`src/app/api/chat/route.ts`)

1. **Rate limit** per IP, then **validate** the body with Zod (Zod caps message
   length at 500).
2. **Retrieve** the top 3 topics with `src/lib/retrieve.ts` (a small TF-IDF /
   phrase-match ranker over `intents.json`; works for Latin and Devanagari).
3. **Out of scope** (best score `< RELEVANCE_THRESHOLD`) → stream a fixed
   refusal in the selected language plus the emergency numbers. **No LLM call.**
4. Otherwise, if `GROQ_API_KEY` is set → **Groq** streaming completion with a
   strict system prompt (answer only from context, never invent numbers, reply
   in the selected language, put emergency numbers first if in danger).
5. If no key (or Groq errors) → **mock** stream of the retrieved answer.
6. **Urgency** is detected by keywords (`src/lib/urgency.ts`) in all three
   languages and reported via the `x-urgency` header, independent of the model.

### Hooks (`src/hooks/`)

- `useChatStream` — `fetch` + `ReadableStream` + `AbortController`; batches UI
  updates with `requestAnimationFrame`; 30s timeout; typed error kinds; reads
  `x-urgency`.
- `useSpeechRecognition` — Web Speech API wrapper. Support is read via
  `useSyncExternalStore` (no hydration mismatch). `interimResults` stream into
  the textarea; language changes stop recognition so the caller can restart.
- `useAutoScroll` — sticky-to-bottom; exposes `showJumpButton` when the user
  scrolls up.
- `useVisualViewportInset` — sets `--keyboard-inset` so the input dock stays
  above the mobile on-screen keyboard.

### Shared lib (`src/lib/`)

`languages.ts` (en/hi/mr + speech locales), `i18n.ts` (all UI strings per
language), `chat-types.ts` (the `Message` type), `chat-protocol.ts` (stream
parsing), `chat-store.ts` (sessionStorage-backed conversation store read with
`useSyncExternalStore`), `preferences.ts` (language / theme / online), `cn.ts`,
`site.ts`, `helplines.ts`, `urgency.ts`, `retrieve.ts`, `answer.ts`,
`rate-limit.ts`.

## Design & accessibility

- Design tokens live in `src/app/globals.css` (Tailwind v4 CSS-first config),
  light + dark via a `.dark` class; theme is applied pre-paint by
  `ThemeScript` and persisted in `localStorage`.
- Fonts: Plus Jakarta Sans (display), Inter (body), JetBrains Mono
  (numbers/helplines), loaded with `next/font`.
- WCAG 2.2 AA: `role="log"`/`role="status"` live regions, keyboard support,
  visible focus rings, ≥44px touch targets, `prefers-reduced-motion` respected,
  icons always paired with text/labels, colour never the only signal.

## Timetable (RailRadar, cache-first)

Runtime chat **never** calls RailRadar (its free tier is ~1,000 requests/month).
Instead, an offline script syncs data into a local JSON store that the chat
tools read from.

```
src/lib/timetable/
  types.ts        Station / Trip / StopTime / TimetableMeta + tool result shapes
  store.ts        TimetableStore interface + JsonTimetableStore (+ Supabase stub)
  time.ts         IST "now" + day-type + duration helpers
  tools.ts        find_station, get_next_trains, get_train_details, get_timetable_info
  groq-tools.ts   Groq function-call definitions + a validated dispatcher
src/data/timetable.json   the dataset (SAMPLE seed until you sync)
scripts/sync-timetable.ts RailRadar → timetable.json
```

**Loading real data:**

```bash
# set RAILRADAR_API_KEY (and optionally RAILRADAR_MONTHLY_BUDGET) in .env.local
npm run sync-timetable          # resumable; --reset to start fresh
```

The script lists Mumbai locals (`/lookup/trains/local?city=Mumbai`), fetches
each train (`/trains/{number}`), sleeps between calls, **stops cleanly on HTTP
429**, tracks requests against the monthly budget, prioritises Western / Central
main / Harbour corridors, and checkpoints progress to
`scripts/.sync-progress.json` so it resumes next run. It writes normalised
`stations`, `trips`, `stop_times`, `meta` (source `"RailRadar (unofficial)"`,
`last_updated`). Verified: `GET /trains/{number}` returns the full ordered stop
list with `arrival`/`departure` (HH:MM, with day offsets for overnight trips)
and platforms.

The tools do same-line direct search and, when there's no direct train, a
one-change interchange search over the stations. Unknown stations or unserved
pairs return `{ covered: false }` so the model says so honestly and points to
the official timetable — it never invents times. `service_type`
(slow/semi_fast/fast/ac) is inferred from halts-per-km and the train name.

To move to Supabase later, implement `TimetableStore` (see the
`SupabaseTimetableStore` sketch in `store.ts`) and swap the exported instance;
tools and API stay unchanged. The shipped `timetable.json` is a small **SAMPLE
seed** with clearly-marked trips so the UI works before a real sync.

## Notes / limitations

- Voice input needs a Chromium or Safari browser and, in most browsers, an
  internet connection; the mic auto-disables where the API is missing (Firefox).
  Typed input is always the primary path.
- The rate limiter is in-memory and per-instance — replace with a shared store
  before running multiple instances.
- The landing page and shared `<Navbar />` are intentionally out of scope for
  this task; `/` is a minimal placeholder that links into `/chat`.
